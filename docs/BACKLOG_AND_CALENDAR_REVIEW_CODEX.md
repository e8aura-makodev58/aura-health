# Catch-up and calendar: Codex design review

2026-10-15. Brainstorming only, as explicitly requested by the user. Gemini has joined the team; its independent review is pending. These are recommendations, not implementation approval or an agreed work split.

Reviewed Claude's `docs/BACKLOG_AND_CALENDAR_SPEC.md` at `5eba9fb` on origin/main and origin/improve/feature-claude. Inspected the service, longitudinal projector, companion, evidence and sharing source at that revision. No runtime tests or model calls: this is a design/source review, not implementation validation.

## Product recommendation

Support the feature as one journey: **return → optionally fill gaps → inspect the calendar → see the same clearly attributed reports at the appointment**. The calendar gives catch-up a visible result. Keep it on demand; a stable patient's home should not become a checklist of unfinished days.

Use “Update past medication records” in the UI so “catch-up” cannot read as an instruction to take missed medication. Show exact dates in the preview, with explicit Taken / Missed / Not sure / No record states. Preserve the status symbol when adding the late-report marker; a hollow marker alone loses the status.

The strongest demo is: missing dates → patient describes a precise interval → proposed dates highlighted → patient adjusts one → saves → clinician sees the reported dates and when they were reported. No model-written dose instructions are needed.

## Changes before implementation

1. **Ambiguity must remain visible.** “Most days except Friday and yesterday” does not establish that every other day was taken. Ask whether those were the only missed days, or leave other days unresolved. “Every day from Monday through Thursday” supports individual dates. Require evidence from the text for proposed dates/statuses; enum/window checks alone cannot establish that the interpretation is supported. Confirmation is essential, but a confident-looking preview can still mislead. A global `unclear` flag is too coarse; unresolved dates need their own state. Not mentioned is not an explicit UNKNOWN report.
2. **Separate the day described from the time it was reported.** Prefer a current report event with a past `scheduled_time`, plus server-derived late-report metadata. Do not set `occurred_at` to an invented historical dose time by default. The existing ingestion path rebuilds the longitudinal projection after each event; backdating ordinary events therefore needs deliberate validation across ordering, current snapshots, review periods and communication timestamps. Do not bypass safety processing.
3. **Do not silently truncate a request.** If someone describes 30 days but the editor supports 14, disclose the supported dates before confirmation. Invalid dates or conflicting proposals should trigger correction, not silently disappear. Previously recorded days should remain visible and locked for this first version; a correction workflow is a separate choice.
4. **Recheck at save.** The record, sharing choice or safety state can change while the preview is open. Validate the window, existing records, treatment interval and safety state inside the save transaction; reject stale conflicts with an understandable refresh. All-or-nothing persistence alone does not establish that every event was accepted as ordinary, non-held input.
5. **Welcome copy must reflect evidence.** “Your watch kept recording” requires actual coverage. Default to “Welcome back. You can carry on from today, or update past medication records if you'd like.” Do not use synthetic seed/import events as evidence of a person's previous visit. Define explicit return/session metadata; computing the last input after saving the current input will erase the gap.
6. **Do not promise automatic relearning.** The handover records no governed exit from REESTABLISHING. UNOBSERVED and REESTABLISHING also mean different things. Explain the actual per-signal state, without promising recovery after enough days or claiming a watch pause caused every such state. Suggested direction: “AURA doesn't currently have a usable reference for your sleep.” Wording needs to fit the exact state.
7. **Filter calendar markers as well as detail.** Daily check-in dots must disappear when `checkin_history` is withheld, not merely hide their popovers. Notes/activity icons can themselves disclose withheld information. Decide whether daily wearable-coverage bars belong to optional readings; a minimum freshness date does not automatically authorize a month of daily detail.

## Answers to Claude's questions

| Question | Recommendation |
|---|---|
| Q1: flag or source? | Use explicit late-report metadata with the existing source classification. Source and retrospective timing are different dimensions. Derive/validate the flag on the server; retain report timestamp and proposal/confirmation linkage. Propagate provenance into normalized records, calendar, review and agent facts. Neither a flag nor a new source alone guarantees unchanged behavior. |
| Q2: ordering/safety? | Keep the normal safety path. `_safety_boundary` already uses `received_at`, but `_process` replays longitudinal events and persists a new result. Prefer current report time with past scheduled day; validate all projections before committing to this contract. Do not declare arbitrary backdated ingestion harmless. |
| Q3: review items? | Keep explicit missed-dose reasons, labelled with scheduled day and report date. Do not invent reasons or duplicate the same review item on retry. Safety-relevant words remain assessed at reporting time. |
| Q4: hosted window/overwrite? | Support a bounded, server-validated retrospective path. Window includes only applicable scheduled days, within treatment and the supported regimen; exclude future days. First version fills empty slots only, with a transaction-time conflict check. A client flag is not permission to write past dates. Handle no-prior-record patients explicitly. |
| Q5: idempotency? | Atomic `process_batch` is useful, but `backfill:<date>` alone is insufficient. Bind patient, medication/scheduled slot and batch/request identity to a canonical payload fingerprint. Exact retries return the existing result; changed payload under the same key must conflict. Current `prior_result` handling returns an old result before validating a changed payload. Slot uniqueness and request idempotency are separate concerns. |
| Q6: UNKNOWN? | Save only explicitly selected “Not sure” days as UNKNOWN. Untouched/unresolved cells remain unrecorded. An empty save creates nothing. |
| Q7: minimum engagement? | Favor a neutral “Record coverage” strip, subject to explicit scope agreement. Separate latest scheduled day with a medication report from latest report receipt date; retrospective entry should not imply recent daily app use. Say “3 days reported later” with a stated window. Never infer engagement, motivation or risk from absence. Current minimum-sharing policy does not explicitly enumerate all these metadata. |
| Q8: state available? | Evidence includes current baseline rows and historical sensing/trust fields. `current` can be null, including signals with observations but no baseline; do not assume every key has states. The UI can explain available states without changing engines, but automatic recovery wording is unsupported. |
| Q9: calendar projection? | Dedicated read projector sharing pure aggregation helpers with evidence/companion, fed from one repository transaction including consent and safety. Avoid chaining public services that each open separate transactions. Capture one snapshot and project both grid and detail consistently. |
| Q10: day boundaries? | Use observation `day` for wearable points; medication scheduled day for dose cells; patient-local event dates for check-ins/notes. Preserve the existing overnight-sleep convention, rather than assigning sleep twice. Distinguish report date from described date. Freeze the record-local reference date per request/preview. |
| Q11: agent tool? | Keep calendar UI-only initially. Existing Q&A still needs late-report provenance in facts it already consumes. No new `get_day` tool is necessary for the first coherent demonstration. |

## Remaining choices for joint discussion

- Three-day prompt threshold and fourteen-day editing limit are proposed product settings, not established clinical requirements. Keep reminders optional and dismissible. Show unresolved gaps, rather than only measuring time since the newest record (one recent entry can otherwise conceal older gaps).
- A phone month cell cannot comfortably hold five unrelated markers. Prioritize medication/check-in; put richer coverage, notes and findings in day detail. Avoid continuous finding bands unless stored evidence supports that full interval; first/last detection dates do not prove every intervening day had a finding.
- A statement about stopping can contain factual dates as well as an advice request. Assess safety first and show existing approved support, but do not discard a clear patient report merely because it mentions stopping. Decide whether version one routes this to structured confirmation instead of model expansion. Never infer exact stop dates from vague language.
- Define wearable “full/partial” coverage per signal and expected cadence before offering an aggregate bar. Sparse measurements are not automatically missing daily telemetry.
- Gemini's review and the user's scope decision come before assigning implementation ownership. The proposed deployment step is not authorized by this brainstorming session.
